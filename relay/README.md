# SkyMyce player relay

Live endpoint: `wss://skyblock-relay.skyblock-relay.workers.dev/websocket`

[Health check](https://skyblock-relay.skyblock-relay.workers.dev/health) · [Cloudflare dashboard](https://dash.cloudflare.com/)

This Cloudflare Worker routes messages between verified Minecraft accounts. Its Durable Objects use hibernating WebSockets. Your PC does not need to remain on. It uses SQLite-backed Durable Objects supported by the Workers Free plan; no paid plan, custom domain, database subscription, or personal Hypixel key is required for the relay.

## Finish in Minecraft

1. Install the newly built `build/libs/skymyce-2.4.1.jar` in your Minecraft instance, replacing the previous SkyMyce JAR. Restart Minecraft. Friends need this version too for relay messages.
2. Join SkyBlock and open `/skymyce pf`. The public relay address is already the default. Settings has a **Reconnect** button with the current connection status on hover. Use it after restarting Minecraft or updating the mod if authentication was rejected, or to reclaim a connection opened elsewhere. It also clears unfinished Join exchanges so you can retry. Connection chatter stays out of normal chat; technical relay/API setup sections remain removed. The `relayUrl` field in `config/skymyce/dungeon_friends.json` remains available for maintenance while Minecraft is closed.
3. **Available** selects the classes you offer when using Join. Automatic acceptance requires a matching relay agreement after choosing **Yes** or **Join**; availability alone never accepts a manual party invitation. The optional **Join PB limit** is your requirement for players requesting to join your party on that floor; blank means no limit. It does not restrict players you explicitly invite.
4. Press **Join** beside an online friend. This works with your background availability off. The button checks your fresh S+ PB against the host's published requirement, and the host checks again before inviting. Changed PB limits and newly fetched shared stats are pushed to connected updated mods, so eligibility changes without pressing Refresh. Host lookups remain a twenty-second fallback while the menu is open. The host must be accepting requests and match the selected floor. Join requests and class offers always use the relay; the normal Hypixel invite and accept commands complete the exchange.
5. Press **Party** to send a regular party invitation for the recipient to accept manually. Press **Invite** to send an LFG request with Yes/No actions. The recipient's mod silently acknowledges receipt. A reconnecting client gets up to five seconds to become ready, then five seconds for the recipient's receipt after transmission. If delivery fails, the ordinary LFG text is sent once through Hypixel `/msg`. Party-size and command-cooldown checks still apply.
6. Incoming LFG requests show the sender, floor, class, and **Yes/No** actions. Yes starts an invitation and automatic acceptance for that specific request, with availability off and without a PB requirement. A plain positive reply to an outstanding LFG also triggers an invitation. Each player's request, inviting, invited, and joined notices replace the preceding notice, leaving one final line. Automatic invitation notices have no Join button. Only confirmations for mod-started actions are compacted; their separate opening/closing border packets are removed. Unrelated party messages keep their normal formatting. Both players need the updated mod for the complete exchange.
7. Pending LFG replies and party invitations mark the player's row with an orange left edge and a warmer background. The status changes to **Invited** after an invitation is sent; joining, declining, or expiry clears the pending marker.
8. Enable **Title notifications** in Settings for invitation and party-join titles. This is off by default and saved between sessions. Normal floors are green, master floors red; Mage is light blue, Tank green, Berserk orange, Archer red, and Healer pink. Ordinary party invitations without floor/class details show a generic title.
9. Your own class-selection messages publish your latest class through the relay. Party Finder class-change notices update the local party and friends list immediately. Updated clients receive broadcasts without refreshing; newer local class observations take priority over later API responses.

Anyone with a verified Minecraft account can connect. The mod only processes messages from known friends. Everyone normally uses the `friends` room; `?room=testing` is a separate allowed room for testing, not a private room. Rooms isolate delivery but are not secret or membership-restricted. Messages are addressed to one player, not broadcast.

The temporary `/skymyce connect` diagnostic has been removed. Automated relay checks remain available to maintainers below.

## Local project and future updates

The maintained source is the `relay` folder in the mod repository. A ready-to-run copy is also installed in `C:\Users\krister\skyblock-relay`, where you created the starter. Its original scaffold is backed up in `codex-original-scaffold`.

From PowerShell, use either project folder:

```powershell
cd 'C:\Users\krister\skyblock-relay'
npm run check
npm test
npm run deploy
```

Your current Cloudflare login is already authorized. If it expires, run `npx wrangler login` and approve the browser page, then deploy again. Cloudflare hosts the relay after the command exits. Keep one source copy authoritative when making future changes; edits to one folder do not automatically update the other.

For local development, run `npm run dev` and set the mod's relay URL to `ws://127.0.0.1:8787/websocket?room=testing`. Real mod clients still need Mojang-signed account proofs; there is no production or development authentication bypass. Restore the hosted address after testing.

Protocol 2 replaces the old `hasJoined` check: Minecraft accepted the local session, but returned HTTP 403 when Cloudflare verified it. Both players must install the updated mod. The client obtains its certificate/profile through Minecraft and signs the relay's challenge locally; the relay makes no requests to the blocked Minecraft endpoints. Connection failures and delivery outcomes go to the Minecraft log without extra chat messages. Delivery IDs correlate with Cloudflare's `relay_delivery` events; neither log includes message bodies or authentication proofs.

The public trust roots in `src/minecraft-keys.json` came from `https://api.minecraftservices.com/publickeys` on 2026-09-22. If Mojang rotates these keys, refresh them from your PC (only the `playerCertificateKeys` and `profilePropertyKeys` arrays), run the checks, and redeploy. Never accept public trust roots supplied by a connecting player. These are public verification keys, not account secrets.

## Behavior and limits

- The relay sends a unique challenge. Minecraft supplies a Mojang-signed, UUID-bound account certificate and a signed profile name. The mod signs the challenge with its local account key. The relay verifies the certificate, ownership signature, profile signature, matching UUID/name, certificate expiry, and profile age (at most 24 hours), then attaches the verified identity to messages. Mojang's signatures use its standard SHA-1/RSA format; the challenge uses SHA-256/RSA with a protocol-specific prefix. Minecraft access tokens, private keys, passwords, and Hypixel API keys never go to the relay.
- Only the addressed mod can acknowledge a delivered message. Unexpired receipts are retained; excess deliveries are rejected before forwarding when the recipient queue/attachment is full. Expired, duplicate, and forged receipts are rejected without forwarding or disconnecting the recipient. Forwarding by the server alone does not count as a client receipt. A dropped acknowledgement can still cause an occasional duplicate LFG message across relay and Hypixel; automatic Join actions never retry through chat.
- Transient failures retry with backoff up to one minute, including unavailable or expired account proofs (4003). Confirmed proof rejection (4004) and an account connected elsewhere (4001) pause until Reconnect or a new Hypixel session. Connections stay open across temporary SkyBlock location/player changes while connected to Hypixel. Deliberate disconnects use the close handshake, with a two-second abort fallback. New messages wait at most five seconds for a ready connection; already transmitted messages are not replayed after reconnecting. Disconnecting from Hypixel cancels pending messages. Outside SkyBlock, the client rejects incoming requests, closes its advertised Join availability, and sends no fallback chat messages. Only one connection per account per room is kept.
- Fixed rooms: `friends` and `testing`. Each room allows 128 connections and at most eight from one IP. New connections are limited to 20 per IP per minute per Cloudflare location. Authentication expires after 30 seconds and permits one proof of at most 8 KiB. Chat payloads are limited to 2 KiB and text to 256 characters. Each connection can burst 12 messages/receipts, then replenishes one every 2.5 seconds. Stats messages allow 8 KiB, burst 30, and replenish one per second.
- Shared stats persist in SQLite with one UUID/name record per player, a ten-minute freshness window, and a 10,000-record cap per room. Verified mod clients supply normalized public stats; these are community reports, not server-verified Hypixel data. A cache miss issues a short-lived upload permission bound to that socket and player. Racing uploads cannot overwrite a fresh record or renew its age. An updated client may also obtain permission to publish newer stats for its own verified account. Stored reports are pushed to updated clients in the same room; clients apply them to tracked players and reject stale or mismatched reports. Lookups enforce a known UUID when supplied. New friends still receive a provider/API lookup and upload only on a cache miss. The client falls back locally if the relay is unavailable. Friend relationships are not stored.
- The `/sm friends` and `/skymyce friends` menu includes offline friends, username search, a local lending ledger, and public wealth totals. Opening it scans the full roster; opening Party Finder still stops at the first offline entry. Automatic scans share a one-minute cooldown. Confirmed SkyBlock profiles and nonplayers are cached locally, and new friends are checked automatically.
- Wealth uses the same SQLite Durable Object with at most 10,000 recent records per room. Each record contains only profile presence, profile name, networth, purse, bank, wardrobe total, and timestamp; no inventories or friend lists are uploaded. Normal results are fresh for 15 minutes; confirmed absence for seven days. Manual refresh queues every known SkyBlock friend, including offline players, reuses shared results under one minute old, and requests older entries again. Repeated manual refreshes have a one-minute client cooldown. A friend previously absent but now in SkyBlock is rechecked.
- Wealth cache misses have a two-minute permission bound to the requesting socket/player. Other clients wait and reuse the result instead of making duplicate API calls. Permissions survive hibernation, and retrying clients reuse their existing permission. Lookups and uploads share a separate six-message burst/one-per-second limit. Totals are returned only to the requesting client. API failures are not published as missing profiles or empty wealth. SkyBlockPv requests are shared across stats and wealth, reuse its cache, and are spaced at least ten seconds apart; failures back off from one to five minutes. Cached relay results remain usable during provider cooldowns.
- Hosts publish their floor, optional Join PB limit, and whether they can invite using authenticated socket attachments. Changed policies are pushed to clients that opt in during authentication; older clients continue using lookups without receiving unsupported messages. Batched lookups return at most 32 requested players in the same room, never disconnected hosts or other clients' claimed identities. Policy traffic has a separate six-request burst/one-per-second allowance. Policies and update opt-ins survive hibernation; pushes use no timers, and no background polling runs when the friends menu is closed.
- Class updates share the existing policy messages, are stamped with the authenticated account's name/UUID, and use the same limits and room isolation. The current class survives socket hibernation and updates any existing SQLite stats record without changing its PB age. API uploads cannot overwrite the current class advertised by an online player. Clients retain live class overrides for the session and release their own override on profile change.
- Hibernation preserves authentication, pending receipts, and per-connection limits in socket attachments. Idle ping/pong uses Cloudflare's automatic response without waking application code. Authentication rejection categories and close code/clean/authenticated state/lifetime are logged. Client failures include the stage, exception types, and call sites; exception messages are omitted because they can contain credentials or response bodies. No chat bodies, proofs, or IP addresses are logged by these diagnostics. Routine invocation logs remain disabled and traces are sampled at 10%. There is no chat history. Cloudflare terminates TLS; this is not end-to-end encrypted messaging.
- The worker's free-plan quotas still apply. Monitor Workers & Pages → **skyblock-relay** → Metrics in Cloudflare. This setup does not enable billing or upgrade your plan.

Wealth capacity check (2026-09-24): normalized records are below 1 KiB, so the 10,000-record limit bounds serialized wealth data below 10 MiB per room before SQLite/index overhead. Queries use the name/UUID indexes; eviction uses the integer primary key and never counts the entire table on each write. A 100-friend cached refresh transfers below roughly 100 KiB of record data, plus request/WebSocket overhead. Cloudflare's [current limits](https://developers.cloudflare.com/durable-objects/platform/limits/) allow 1 GB per free SQLite Durable Object and 5 GB total. [Free daily allowances](https://developers.cloudflare.com/durable-objects/platform/pricing/) are 5 million rows read, 100,000 rows written, and 100,000 compute requests; index changes and deletes also consume writes. These limits are shared with the existing relay and other account workloads, so the storage bound is not a promise of unlimited refresh traffic. No additional service, binding, polling timer, or billing plan is required.

## Verification

### Daily Digest news and RNG

The Daily Digest reuses this authenticated WebSocket and SQLite room. It adds no service, binding, cron job, or background polling loop. Old clients receive no RNG packets unless they explicitly subscribe. `ready` advertises `digestNews` and `rngFeed` so new clients also work with older relays.

**Cowshed setup:** there is no Cowshed bridge or Discord credential in the mod. [Cowshed's maintainer](https://cowtipper.de/moonitor) supports following announcement channels into another Discord server. Follow **#game-updates** and **#alpha-updates** into two dedicated channels in a server you administer, or use the original channels if your authorized bot has access. Check the current source names in Cowshed; never point these settings at private discussions. Give a dedicated bot only View Channel and Read Message History in those two channels, and enable Discord's Message Content intent where required. The bridge makes read-only requests; it never posts or manages Discord messages.

Set the deployment's `DIGEST_GAME_CHANNEL` and `DIGEST_ALPHA_CHANNEL` variables to those two channel IDs. Store the bot credential only as a Worker secret using `npx wrangler secret put DISCORD_NEWS_TOKEN`. Keep local credentials in ignored `.dev.vars`, never the client or Git. These settings are optional: until configured, the news card reports that the source is unavailable and the rest of the digest continues to work. No Discord login is required from players.

Operator setup:

1. Create two dedicated announcement mirror channels in your own Discord server. In Cowshed, use each requested announcement channel's **Follow** action to send its published announcements to the matching mirror. Following does not backfill old posts. If a source cannot be followed, obtain authorized read access from its owner instead; this bridge does not bypass channel permissions.
2. Create an application and bot in the [Discord Developer Portal](https://discord.com/developers/applications). Enable **Message Content Intent** in the bot settings if required for its content access. Invite the bot to your server with the `bot` scope and only **View Channel** and **Read Message History** for those mirrors. Sending messages, administration, and member/presence access are unnecessary.
3. Enable Discord Developer Mode, right-click each mirror, and copy its channel ID. Add `DIGEST_GAME_CHANNEL` and `DIGEST_ALPHA_CHANNEL` to `vars` in `relay/wrangler.jsonc`, retaining the existing `ROOMS` variable. Channel IDs are configuration; the bot token is a secret and must never go in this file.
4. From the `relay` directory, run `npx wrangler secret put DISCORD_NEWS_TOKEN` and enter the bot token at Wrangler's secret prompt. Do not paste the token into a shell command, log, issue, or pull request. For local development only, set these three values in the ignored `.dev.vars` file.
5. Run `npm run check`, `npm test`, and then `npm run deploy` for the intended Cloudflare account. Open `/sm digest`, enable the desired news sources, and refresh. An empty newly followed channel remains empty until Cowshed publishes a new announcement.
6. If the card reports unavailable, verify the source/mirror IDs, bot membership, channel permissions, and Message Content Intent. HTTP 200 responses whose messages contain no usable content are treated as invalid responses, preserving the cache. Discord authentication errors and rate limits are surfaced without exposing credentials. Rotate an exposed token in Discord and replace the Worker secret.

Each channel retains eight sanitized items (160-character titles, 2,500-character content with a truncation indication). A request refreshes at most once per five minutes per room, deduplicates in-flight work, and uses the last Discord message ID to fetch only newer messages. The bridge supports ordinary content, embed fields, followed announcements, and forwarded snapshots. The upstream response is bounded to 256 KiB with an eight-second timeout; each downstream news packet stays below 32 KiB. Refresh errors preserve cached items and back off from five to thirty minutes, honoring longer Discord rate limits. Historic edits and deleted announcements are not synchronized by the incremental cache. Images and attachments are not downloaded. A stale timestamp always describes the last successful fetch, not the last attempt.

RNG receiving and sharing are separate client opt-ins. Only locally detected, allowlisted rare dungeon/slayer acquisitions can be submitted; the initial catalog contains Necron's Handle, Giant's Sword, Dark Claymore, Shadow Fury, the three Wither scrolls, Warden Heart, Judgement Core, and Overflux Capacitor. Kuudra/fishing are reserved activity types with no accepted items until reliable detectors are implemented. Community claims remain **unverified**: Minecraft authentication proves the reporting account, not the drop itself.

An RNG submission contains a random event ID, allowlisted item ID, activity, acquisition timestamp, and whether to show the authenticated player name. The server rejects extra fields, ordinary loot, future/old timestamps, malformed IDs, and oversized requests. No inventory, chat text, coordinates, friend roster, purse/bank values, private API payload, profile, or client-supplied IP address belongs in this protocol. Existing Minecraft account proof authenticates the socket; no Hypixel or Discord credentials are sent by players. The public event contains only a fresh server-generated random ID, item, activity, timestamp, `unverified: true`, and either the authenticated Minecraft name or `Anonymous`. The private account UUID and client event ID are never broadcast, even in anonymous mode.

The server accepts at most three new reports per minute per account, with deduplication and rate limits persisting through reconnections and hibernation. Rate records expire after six minutes (including allowed clock skew); public history retains at most 200 events from the last seven days and subscriptions receive at most 30 initially. Expired records are pruned on the next read or submission. Per-session digest requests additionally allow a burst of six, replenishing one per five seconds. Disabling receiving is honored even when rate limited. Public history stores the private reporting UUID only for abuse prevention/deduplication alongside the sanitized event; it is not exposed to peers or logged. Changing name visibility affects future reports; clearing local history does not retract already shared events. The server does not upload historical local events or send congratulatory chat messages.

Protocol: `digest_news_get` / `digest_news_result`, `rng_subscribe` / `rng_result`, `rng_publish` / `rng_result`, and subscribed `rng_event` pushes. News and RNG failures are independent of party/stats/wealth delivery. News requests accept only `game` or `alpha` sources and cannot select arbitrary upstream URLs.

Sources: [Discord channel history and message shapes](https://docs.discord.com/developers/resources/message#get-channel-messages), [Discord rate limits](https://docs.discord.com/developers/topics/rate-limits), [Worker secrets](https://developers.cloudflare.com/workers/configuration/secrets/), [Durable Object WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/).

`npm run check` generates Cloudflare types and checks TypeScript. `npm test` packages the production Worker and runs real local WebSocket connections in Miniflare. Only the public trust roots in the in-memory test bundle are replaced with generated test keys. Real signature verification checks cover valid proofs, forged names/UUIDs, certificate/profile expiry, signature tampering, replay rejection, identity stamping, recipient acknowledgements, hibernation/resumption, room isolation, message sizes, and message-rate limits. The mod's Gradle checks also cover receipt timeout/fallback, cancellation, PB checks, and party behavior.

`npm run smoke` checks live protocol/health and unauthenticated rejection without account credentials. An approved real-account check also passed against the deployed relay: signed certificate/profile verification, heartbeats before and after 35 seconds idle, and a clean close. Two-player GUI behavior requires the in-game steps above.
